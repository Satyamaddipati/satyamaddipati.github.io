Case study

AI Life Logger.

A personal systems-engineering project: audio captured on Ray-Ban glasses becomes structured memories and an hourly summary, with no cloud dashboard and no manual review step.

Personal project · code not yet linked

01

Why this is a systems problem, not just an LLM demo

Calling an LLM on a transcript is the easy part. The actual engineering is in the plumbing around it: audio arrives continuously and unpredictably, has to be turned into text reliably, filtered down to what's worth remembering, summarized, stored durably, and delivered on a schedule — without a person babysitting any of it.

02

Architecture

  • Ray-Ban glasses capture audio
  • A filesystem watcher picks up new recordings as they land
  • Whisper transcribes them
  • A filtering/deduplication step discards noise and repeats
  • Claude summarizes what's left into structured notes
  • SQLite persists the result
  • A Telegram bot delivers an hourly digest

03

What a pipeline like this has to get right

Running unattended against a continuous audio stream raises a specific set of problems, independent of the model in the loop:

  • Partial writes. A recording interrupted mid-capture shouldn't produce a half-transcribed, corrupted entry.
  • Duplicate captures. If the watcher sees the same file twice — a retry, a sync hiccup — it shouldn't summarize it twice.
  • Quiet hours. Not every captured moment should become a 2 a.m. Telegram notification.
  • Failure recovery. A Whisper or Claude API failure on one clip shouldn't take down the rest of the pipeline.
  • Privacy by default. Everything stays local (SQLite, no cloud dashboard); the only outbound step is the summary itself.

These are the design constraints the architecture above is built to satisfy — the project's engineering substance, not a list of logged incidents.
